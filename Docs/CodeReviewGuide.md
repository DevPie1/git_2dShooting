# Unity C# 코드 리뷰 기준

## 리뷰 원칙

* 변경된 코드에서 실제로 발생할 가능성이 있는 문제를 우선한다.
* 단순한 취향 차이나 과도한 리팩터링을 반드시 수정해야 하는 문제처럼 표현하지 않는다.
* 문제를 발견하면 해당 파일과 코드 위치, 문제의 원인, 발생할 수 있는 결과를 구체적으로 설명한다.
* 가능하면 현실적인 수정 방법이나 간단한 코드 예시를 함께 제시한다.
* 변경된 코드와 직접 관련 없는 기존 문제는 별도의 참고사항으로 구분한다.
* 확실하지 않은 내용은 사실처럼 단정하지 않는다.
* 코드의 규모와 프로젝트 단계를 고려하여 적절한 수준의 개선안을 제안한다.
* 디자인 패턴이나 추상화를 무조건 적용하지 않는다.

## 중요도 기준

* Critical: 크래시, 데이터 손상, 보안 문제처럼 즉시 수정해야 하는 문제
* High: 기능 오류나 심각한 성능 저하로 이어질 가능성이 높은 문제
* Medium: 안정성, 확장성, 유지보수성을 위해 수정이 권장되는 문제
* Low: 가독성, 네이밍, 코드 단순화처럼 선택적으로 개선할 수 있는 사항

## 가독성과 유지보수성

### 이름을 통해 의도를 알 수 있는가?

* 클래스, 메서드, 변수 이름이 실제 역할을 명확하게 나타내는지 확인한다.
* `data`, `value`, `temp`, `manager`처럼 의미가 지나치게 넓은 이름이 남용되지 않았는지 확인한다.
* `bool` 변수는 상태를 자연스럽게 읽을 수 있는 이름인지 확인한다.

    * 예: `isDead`, `canAttack`, `hasTarget`
* 메서드 이름은 수행하는 동작을 동사 형태로 명확하게 표현하는지 확인한다.

### 매직 넘버를 사용하고 있지 않은가?

코드의 의미를 이름만으로 파악하기 어려운 숫자를 직접 사용하지 않았는지 확인한다.

```csharp
if (currentLevel >= 10)
{
    damage *= 1.5f;
}
```

`10`, `1.5f`가 게임 규칙에서 특별한 의미를 가진다면 상수나 설정값으로 분리하도록 제안한다.

```csharp
private const int SpecialLevel = 10;
private const float SpecialDamageMultiplier = 1.5f;
```

Unity Inspector에서 조정해야 하는 값이라면 `[SerializeField]`를 사용하는 방법도 고려한다.

```csharp
[SerializeField] private int specialLevel = 10;
[SerializeField] private float specialDamageMultiplier = 1.5f;
```

다음과 같이 의미가 명확하고 관용적으로 사용되는 값은 불필요하게 상수로 분리하지 않아도 된다.

* `0`: 초기화, 비어 있음, 최소값 검사
* `1`: 1만큼 증가, 기본 배율, 단위 방향
* `-1`: 검색 실패, 존재하지 않음을 나타내는 인덱스
* 반복문의 시작값과 증감값

다만 `-1`, `0`, `1`이라도 코드만 보고 의미를 파악하기 어렵다면 이름 있는 상수나 열거형으로 분리하도록 제안한다.

특히 다음 값이 코드 곳곳에 직접 작성되어 있다면 우선적으로 확인한다.

* 플레이어 체력과 공격력
* 이동속도와 회전속도
* 쿨타임과 지속시간
* 경험치와 레벨 기준
* 확률과 가중치
* 레이어 번호
* 애니메이션 상태 번호
* 최대 개수와 제한 횟수
* 데미지 배율
* 씬 인덱스

## 객체지향 설계

### 묻지 말고 시켜라

객체의 내부 데이터를 외부에서 가져온 뒤 외부 객체가 상태를 판단하고 행동을 결정하는 구조를 확인한다.

다음과 같은 구조는 객체의 내부 구현이 외부에 노출되고 객체 간 결합도가 높아질 수 있다.

```csharp
if (player.Health <= 0)
{
    player.Die();
}
```

가능하면 객체에 필요한 행동을 요청하고, 상태 판단과 세부 처리는 해당 객체가 담당하도록 제안한다.

```csharp
player.TakeDamage(damage);
```

`Player`는 `TakeDamage()` 내부에서 다음 내용을 스스로 처리할 수 있다.

* 체력 감소
* 사망 여부 판단
* 사망 처리
* 관련 이벤트 발생

리뷰할 때 다음 내용을 확인한다.

* 객체의 상태를 외부에서 반복적으로 조회하고 있지 않은가?
* 외부 객체가 다른 객체의 내부 상태를 지나치게 많이 알고 있지 않은가?
* 데이터를 가져와 외부에서 판단하기보다 객체에 행동을 요청할 수 있는가?
* 여러 클래스에서 같은 상태 판단이 중복되고 있지 않은가?
* Getter와 프로퍼티를 통해 객체의 내부 구현이 과도하게 노출되고 있지 않은가?

단, 단순 조회가 자연스러운 UI 표시, 디버깅, 저장 및 직렬화까지 무조건 행동 메서드로 바꾸도록 요구하지 않는다.

### 응집도는 높고 결합도는 낮은가?

* 하나의 클래스에 서로 관련 없는 기능이 섞여 있지 않은지 확인한다.
* 관련된 데이터와 동작이 같은 클래스 또는 모듈에 모여 있는지 확인한다.
* 하나의 클래스가 너무 많은 다른 클래스를 직접 참조하고 있지 않은지 확인한다.
* 다른 클래스의 구체적인 구현 방식에 지나치게 의존하고 있지 않은지 확인한다.
* 작은 변경 하나가 여러 클래스의 수정으로 이어지는 구조인지 확인한다.
* 전역 상태와 Singleton에 불필요하게 의존하고 있지 않은지 확인한다.
* 클래스 간 참조가 순환하고 있지 않은지 확인한다.

응집도가 지나치게 낮거나 결합도가 지나치게 높다면 단순히 “구조가 좋지 않다”고만 작성하지 않고 다음 내용을 포함한 개선 방향을 제안한다.

1. 어떤 책임을 분리해야 하는가?
2. 어떤 클래스가 해당 책임을 가져야 하는가?
3. 클래스 사이의 의존성을 어떻게 줄일 수 있는가?
4. 이벤트, 인터페이스, 컴포지션 중 어떤 방법이 적절한가?
5. 변경 후 클래스 간 관계가 어떻게 달라지는가?

## SOLID 원칙

SOLID 원칙을 기준으로 설계를 검토하되, 모든 코드에 인터페이스와 디자인 패턴을 강제하지 않는다.

규모가 작고 변경 가능성이 낮은 코드에는 단순한 구조가 더 적절할 수 있다.

### SRP: 단일 책임 원칙

클래스가 변경되는 이유를 하나의 책임으로 설명할 수 있는지 확인한다.

예를 들어 하나의 `Player` 클래스가 다음 기능을 모두 처리한다면 책임 분리를 검토한다.

* 입력 처리
* 이동
* 공격
* 체력
* 애니메이션
* 사운드
* 저장
* UI 갱신

책임이 지나치게 많다면 다음과 같이 역할별 컴포넌트 분리를 제안할 수 있다.

```text
PlayerInput
PlayerMovement
PlayerCombat
PlayerHealth
PlayerAnimation
```

단, 메서드 수가 많다는 이유만으로 무조건 클래스를 분리하지 않는다. 서로 밀접한 상태와 행동까지 과도하게 나누면 오히려 결합도가 높아질 수 있다.

### OCP: 개방-폐쇄 원칙

새로운 기능이나 타입을 추가할 때 기존 조건문을 계속 수정해야 하는 구조인지 확인한다.

```csharp
if (enemyType == EnemyType.Normal)
{
}
else if (enemyType == EnemyType.Chase)
{
}
else if (enemyType == EnemyType.Boss)
{
}
```

Enemy 종류가 계속 추가될 예정이라면 상속, 인터페이스, 전략 패턴 또는 컴포지션을 이용한 확장 구조를 제안한다.

다만 종류가 적고 더 이상 확장되지 않는 단순한 조건문에 불필요한 추상화를 강요하지 않는다.

### LSP: 리스코프 치환 원칙

부모 타입을 사용하는 위치에 자식 타입을 넣었을 때 기존 동작이 깨지지 않는지 확인한다.

* 자식 클래스가 부모 메서드의 의미를 완전히 바꾸고 있지 않은가?
* 자식 클래스가 부모 기능을 사용할 수 없어 예외를 던지고 있지 않은가?
* 자식 클래스 때문에 사용하는 쪽에서 타입 검사를 추가해야 하지 않는가?

상속 관계가 자연스럽지 않다면 상속 대신 컴포지션이나 별도 인터페이스를 제안한다.

### ISP: 인터페이스 분리 원칙

클래스가 사용하지 않는 기능까지 구현하도록 강요받고 있지 않은지 확인한다.

```csharp
public interface ICharacter
{
    void Move();
    void Attack();
    void Fly();
    void Swim();
}
```

모든 캐릭터가 비행하거나 수영하지 않는다면 역할별 인터페이스 분리를 제안한다.

```text
IMovable
IAttackable
IFlyable
ISwimmable
```

단, 메서드가 하나뿐인 인터페이스를 무분별하게 생성하도록 제안하지 않는다.

### DIP: 의존성 역전 원칙

상위 수준의 게임 로직이 특정 구현 클래스에 직접 의존하고 있지 않은지 확인한다.

다음과 같은 구조가 확장과 테스트를 어렵게 만드는지 검토한다.

```csharp
private KeyboardInput keyboardInput = new KeyboardInput();
```

키보드, 모바일 터치, AI 입력 등 여러 구현으로 교체해야 한다면 인터페이스나 추상 타입에 의존하도록 제안한다.

```csharp
private IPlayerInput playerInput;
```

Unity 프로젝트에서는 다음 방식을 상황에 맞게 고려한다.

* Inspector를 통한 컴포넌트 참조
* 생성자 또는 메서드를 통한 의존성 전달
* 인터페이스를 구현한 컴포넌트 사용
* ScriptableObject를 이용한 데이터와 설정 분리
* 이벤트를 이용한 객체 간 직접 참조 감소

## 설계 구조 개선 제안 기준

다음 문제가 명확하게 나타날 때는 단순한 코드 수정에 그치지 않고 설계 구조 개선안을 제안한다.

* 하나의 클래스가 너무 많은 책임을 담당한다.
* 비슷한 조건문이 여러 클래스에서 반복된다.
* 새로운 기능을 추가할 때 기존 코드를 광범위하게 수정해야 한다.
* 객체들이 서로의 내부 상태를 지나치게 많이 알고 있다.
* 구체 클래스에 대한 의존성이 강해 교체와 테스트가 어렵다.
* 상속 구조에서 자식 클래스가 부모 클래스의 계약을 지키지 못한다.
* Singleton과 전역 상태에 대한 의존성이 지나치게 높다.
* 클래스 간 순환 참조가 발생한다.
* 변경 하나가 연쇄적인 수정으로 이어진다.

설계 개선안을 제시할 때는 다음 형식으로 설명한다.

### 현재 구조의 문제

현재 어떤 책임과 의존성 때문에 유지보수 또는 확장이 어려운지 설명한다.

### 개선 구조

어떤 클래스, 컴포넌트 또는 인터페이스로 역할을 분리할지 제안한다.

### 클래스별 책임

각 클래스가 담당할 역할을 명확하게 작성한다.

### 객체 간 상호작용

객체들이 어떤 메서드, 인터페이스 또는 이벤트를 통해 상호작용할지 설명한다.

### 적용 시 주의점

개선으로 얻는 장점과 함께 클래스 수 증가, 추상화 비용 등의 단점도 설명한다.

## C# 확인 항목

* NullReferenceException이 발생할 가능성이 있는가?
* 컬렉션의 범위를 벗어나 접근할 가능성이 있는가?
* 이벤트를 구독한 후 적절한 시점에 해제하는가?
* `IDisposable` 객체나 리소스를 올바르게 정리하는가?
* 불필요한 박싱이나 문자열 생성이 반복되는가?
* 성능에 민감한 코드에서 LINQ가 반복적으로 실행되는가?
* public 필드가 불필요하게 노출되어 있지 않은가?
* 캡슐화를 깨뜨리는 프로퍼티가 과도하게 사용되고 있지 않은가?
* 예외 상황과 실패 가능성이 적절하게 처리되고 있는가?
* 비동기 작업의 예외와 취소가 처리되고 있는가?
* 동일한 코드나 조건 판단이 여러 곳에서 중복되고 있지 않은가?

## Unity 확인 항목

* `Update()` 또는 `FixedUpdate()`에서 불필요한 객체 할당이 반복되는가?
* `Find`, `FindObjectOfType`, `GetComponent` 등의 탐색이 매 프레임 반복되는가?
* 물리 처리가 `Update()`에서 프레임 의존적으로 실행되고 있지 않은가?
* Coroutine, Invoke, async 작업이 오브젝트 생명주기 이후에도 남을 가능성이 있는가?
* Unity 이벤트 함수의 실행 순서에 과도하게 의존하고 있지 않은가?
* `Instantiate()`와 `Destroy()`가 반복되어 오브젝트 풀링이 필요한가?
* 파괴된 `UnityEngine.Object`의 Null 판정 방식을 고려했는가?
* Inspector에서 반드시 할당해야 하는 참조가 검증되고 있는가?
* `Awake()`, `OnEnable()`, `Start()`의 역할이 적절하게 구분되어 있는가?
* `OnEnable()`에서 등록한 이벤트를 `OnDisable()`에서 해제하고 있는가?
* 시간 기반 처리에 `Time.deltaTime` 또는 고정 물리 시간을 적절하게 사용하고 있는가?
* 문자열로 태그, 레이어, 애니메이션 상태를 반복 참조하고 있지 않은가?
* 런타임에 변경되는 데이터와 원본 설정 데이터가 적절하게 분리되어 있는가?

## 캐싱 및 캐시 히트 효율

Unity에서 반복적으로 접근하거나 탐색하는 객체와 컴포넌트를 적절하게 캐싱하고 있는지 확인한다.

단순히 "캐싱을 사용했는가"만 확인하지 않고, **반복 탐색 비용을 줄이고 실제 캐시 히트율을 높이는 구조인지**를 기준으로 검토한다.

### 반복 탐색 결과를 캐싱하고 있는가?

다음과 같이 매번 동일한 객체나 컴포넌트를 탐색하는 코드가 반복되는지 확인한다.

```csharp
void Update()
{
    GetComponent<Rigidbody>().velocity = velocity;
}
```

반복적으로 동일한 컴포넌트를 조회한다면 초기화 시점에 캐싱하는 것을 고려한다.

```csharp
private Rigidbody rb;

private void Awake()
{
    rb = GetComponent<Rigidbody>();
}
```

다음과 같은 탐색도 반복된다면 캐싱을 우선적으로 검토한다.

* `GetComponent<T>()`
* `GetComponentInChildren<T>()`
* `GetComponentInParent<T>()`
* `Find()`
* `FindObjectOfType()`
* `FindFirstObjectByType()`
* `Camera.main`
* 반복적인 Dictionary/Collection 검색
* 자주 사용하는 `Transform`, `Animator`, `Rigidbody`, `Collider` 등의 참조

단, 한 번만 실행되는 초기화 코드까지 무조건 캐싱하도록 요구하지 않는다. **반복 호출 빈도와 실제 비용을 기준으로 판단한다.**

### 캐시를 사용하고 있지만 캐시 히트율이 낮아지지 않는가?

캐싱된 객체를 사용하지 않고 매번 새로운 탐색을 수행하거나, 캐시가 자주 무효화되어 다시 탐색하는 구조인지 확인한다.

예를 들어 다음과 같이 캐싱된 참조가 있음에도 매번 검색한다면 캐싱 효과가 감소한다.

```csharp
private Transform target;

void Update()
{
    target = GameObject.Find("Player").transform;
}
```

가능하면 초기화 또는 대상 변경이 발생하는 시점에만 참조를 갱신한다.

```csharp
private Transform target;

private void Awake()
{
    target = GameObject.Find("Player").transform;
}
```

특히 다음 상황을 확인한다.

* 매 프레임 캐시를 다시 생성하거나 덮어쓰고 있지 않은가?
* 캐시가 있는데 동일한 객체를 다시 탐색하고 있지 않은가?
* 불필요하게 캐시를 초기화하여 Hit보다 Miss가 자주 발생하지 않는가?
* 대상이 변경될 때만 캐시를 갱신하도록 구성할 수 있는가?
* 객체가 파괴되었거나 교체된 경우 오래된 참조를 계속 사용하지 않는가?

### Dictionary와 Collection을 활용한 빠른 조회

동일한 ID, 타입, 이름 등을 기준으로 객체를 반복 검색한다면 선형 탐색을 반복하는 대신 적절한 자료구조를 사용하는 것을 고려한다.

예를 들어 다음과 같은 코드가 반복된다면:

```csharp
var enemy = enemies.Find(x => x.Id == enemyId);
```

객체 수가 많거나 검색 빈도가 높다면 `Dictionary`를 이용하여 조회 비용을 줄이는 방법을 검토한다.

```csharp
private Dictionary<int, Enemy> enemyCache;

public Enemy GetEnemy(int id)
{
    return enemyCache.TryGetValue(id, out var enemy)
        ? enemy
        : null;
}
```

다음과 같은 경우 Dictionary 등의 캐시 구조를 우선적으로 검토한다.

* 동일한 키를 반복적으로 검색한다.
* 객체 수가 많다.
* 검색이 `Update()` 또는 반복되는 게임 로직에서 발생한다.
* `List.Find()`, LINQ `FirstOrDefault()` 등의 선형 검색이 반복된다.

단, 객체 수가 매우 적거나 검색 빈도가 낮다면 Dictionary를 추가하는 것이 오히려 코드 복잡도만 증가시킬 수 있으므로 실제 사용 빈도와 데이터 규모를 고려한다.

### 캐시 무효화(Cache Invalidation)를 적절하게 처리하는가?

캐싱은 참조를 저장하는 것뿐만 아니라 **언제 캐시를 갱신하거나 폐기해야 하는지**도 중요하다.

다음과 같은 상황에서 오래된 캐시가 사용되지 않는지 확인한다.

* 대상 GameObject가 `Destroy()`됨
* 대상이 씬 전환으로 변경됨
* 풀링된 객체가 재사용됨
* 플레이어 또는 타겟이 변경됨
* 데이터가 갱신됨
* Dictionary에서 객체가 제거됨

캐시가 무효화될 수 있다면 해당 시점에 명확하게 갱신하거나 제거하는 구조를 제안한다.

```csharp
public void SetTarget(Transform newTarget)
{
    target = newTarget;
}
```

캐시 무효화 처리가 누락되면 `NullReferenceException`, 파괴된 객체 참조, 잘못된 대상 접근 등의 문제가 발생할 수 있으므로 기능 오류 가능성이 있는 경우 우선적으로 지적한다.

### 캐싱과 객체 풀링을 함께 고려하는가?

`Instantiate()`와 `Destroy()`가 반복되는 구조에서는 단순히 생성 비용만 줄이는 것이 아니라 **생성된 객체와 컴포넌트 참조를 재사용할 수 있는지** 확인한다.

예를 들어 투사체를 반복 생성하는 경우:

```text
Instantiate
    ↓
GetComponent
    ↓
사용
    ↓
Destroy
```

보다 다음과 같이 풀링된 객체를 재사용하는 구조를 고려한다.

```text
Pool에서 객체 획득
    ↓
이미 캐싱된 컴포넌트 사용
    ↓
사용
    ↓
Pool 반환
```

특히 다음과 같은 반복 객체를 우선적으로 확인한다.

* 총알
* 적
* 이펙트
* 데미지 숫자
* 파티클
* UI 요소

단, 생성 빈도가 낮은 객체까지 무조건 풀링하도록 요구하지 않는다.

### 캐시 효율을 성능 문제로 판단할 때

캐싱 자체를 목적처럼 다루지 않는다.

다음 요소를 함께 고려하여 실제 최적화 필요성을 판단한다.

* 호출 빈도
* 객체 수
* 탐색 비용
* 실행 위치 (`Update`, `FixedUpdate`, Coroutine 등)
* 해당 코드가 실행되는 프레임 수
* 실제 프로파일링 결과
* 캐싱으로 증가하는 메모리 사용량
* 캐시 무효화 관리 비용

특히 `Update()`에서 수백~수천 개의 객체가 반복적으로 `GetComponent`, `Find`, `List.Find`, LINQ 등을 호출하는 경우 우선적으로 확인한다.

반대로 초기화 단계에서 한 번 실행되는 탐색까지 무조건 캐싱 최적화 대상으로 지적하지 않는다.

### 캐싱 리뷰 시 우선순위

다음 순서로 실제 성능 영향이 큰 문제를 우선적으로 검토한다.

1. 매 프레임 반복되는 `Find`, `FindObjectOfType`, `GetComponent`
2. 다수의 객체에서 반복되는 컴포넌트 탐색
3. 반복적인 선형 Collection 검색
4. 반복되는 LINQ 및 임시 객체 생성
5. 캐시가 있음에도 다시 수행되는 탐색
6. 캐시 무효화로 인해 불필요하게 반복되는 탐색
7. 객체 풀링과 함께 최적화할 수 있는 반복 생성/탐색
8. 성능 영향이 작은 단순 접근의 캐싱

**캐싱을 사용하지 않았다는 사실만으로 문제로 지적하지 않는다.** 실제 반복 횟수와 비용이 충분히 크고 성능에 영향을 줄 가능성이 있는 경우에만 중요도를 높여 지적한다.


## 리뷰 결과 형식

다음 형식으로 답변한다.

### 총평

변경 목적과 전체적인 평가를 2~3문장으로 작성한다.

### 발견된 문제

각 문제에 다음 내용을 포함한다.

1. 중요도
2. 파일 및 코드 위치
3. 문제 설명
4. 발생할 수 있는 결과
5. 수정 제안

### 설계 개선 제안

SOLID 위반, 낮은 응집도, 높은 결합도 등 구조적인 문제가 명확할 때만 작성한다.

단순히 디자인 패턴의 이름만 제시하지 말고 다음 내용을 설명한다.

* 현재 구조의 문제
* 분리하거나 추가할 클래스
* 각 클래스의 책임
* 객체 간 상호작용 방법
* 개선으로 얻는 장점과 비용

### 잘 작성된 점

실제로 잘 작성된 부분이 있을 때만 간단히 작성한다.

문제를 찾지 못했다면 억지로 문제를 만들지 말고, 확인한 범위와 문제가 발견되지 않았음을 명시한다.
